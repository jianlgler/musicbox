# Object storage: SeaweedFS

Audio files live in object storage, not in Postgres. Postgres keeps facts about a track
(title, size, status); object storage keeps the bytes.

## Why object storage

| Option | Problem |
| --- | --- |
| In Postgres (`bytea`) | Backups and replicas carry all the audio; large blobs slow the database |
| On the API's local disk | Only works with one instance; the streaming service (W19) can't see the files; lose the machine, lose the music |
| **Object storage (S3 API)** | Built for large immutable blobs, shared by every instance over HTTP, scales separately from the database |

## How object storage works

A flat key → blob store, spoken over HTTP:

```
bucket: musicbox
  key: audio/<sha256>   → the audio bytes
```

- No real folders: `audio/` is part of the key name.
- Objects are written whole and never modified in place. Reads can ask for a byte range,
  which is how streaming and seeking will work.
- Keys are content-addressed: the key is the file's SHA-256, so the same file uploaded twice
  is stored once. The `tracks.sha256` column links a row to its object.

## Why the S3 API

The S3 API is the industry standard, spoken by AWS S3, Cloudflare R2, Backblaze B2, Ceph and
SeaweedFS. Code that speaks S3 moves from this laptop to AWS, or to the NAS later, by changing
an endpoint URL and a key pair.

## Why SeaweedFS

- Gives an S3 API locally in one container.
- MinIO community edition, the usual choice, stopped shipping images in October 2025 and its
  repository was archived.
- It's also the planned storage for the NAS, so it's learned once.

### Its parts

One `weed server` process runs all of them, which is fine for development:

```
weed server
 ├── master   tracks which volume holds which data
 ├── volume   stores the bytes, packed into large volume files
 ├── filer    maps names (keys) to stored data
 └── s3       S3 API gateway on port 8333: the only part the code talks to
```

In production these run as separate processes and scale independently.

## Security

| Measure | Why |
| --- | --- |
| The API's S3 identity can only Read, Write and List on bucket `musicbox`, no `Admin` | A compromised API can't create buckets, change permissions, or reach other buckets |
| Keys generated by `scripts/gen-secrets.sh` into git-ignored files | No secret is typed by hand or committed; every clone gets its own keys |
| S3 port published on `127.0.0.1:8333` only; master, volume and filer ports not published | Same reason as Postgres: Docker bypasses `ufw` |
| Image pinned by digest (`@sha256:…`), not only by tag | Tags can be moved to different contents; a digest names exact bytes (supply-chain control) |

## Setup

### 1. Secrets: `scripts/gen-secrets.sh`

```sh
./scripts/gen-secrets.sh
```

- Adds missing variables to `.env`: `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY` (20 hex chars),
  `S3_SECRET_KEY` (40 hex chars, 160 bits). It also creates the Postgres variables on a fresh clone.
- **Never overwrites an existing value.** Postgres reads `POSTGRES_PASSWORD` only when it first
  creates its volume, so regenerating it would lock the API out.
- Writes `seaweedfs/s3.json` from `.env` on every run (`.env` is the single source of truth).
- Never prints a secret, only `kept` or `generated` plus the variable name.
- Both files are `chmod 600`; `seaweedfs/s3.json` is git-ignored like `.env`.

The identity it writes:

```json
{
  "identities": [
    {
      "name": "musicbox-api",
      "credentials": [{ "accessKey": "…", "secretKey": "…" }],
      "actions": ["Read:musicbox", "Write:musicbox", "List:musicbox"]
    }
  ]
}
```

There's no anonymous identity, so unsigned requests are refused.

**Rotating the keys:** delete the `S3_ACCESS_KEY` and `S3_SECRET_KEY` lines from `.env`, rerun
the script, then `docker compose restart seaweedfs`.

### 2. The Compose service

```yaml
seaweedfs:
  image: chrislusf/seaweedfs:4.48@sha256:4e61d15f…72d
  restart: unless-stopped
  command: [server, -dir=/data, -ip.bind=0.0.0.0, -s3, -s3.port=8333, -s3.config=/etc/seaweedfs/s3.json]
  ports: ["127.0.0.1:8333:8333"]
  volumes:
    - seaweeddata:/data
    - ./seaweedfs/s3.json:/etc/seaweedfs/s3.json:ro
  healthcheck: wget http://127.0.0.1:8333/status
```

- `-ip.bind=0.0.0.0` is *inside* the container (required so Docker's port forwarding reaches
  it). What's exposed on the host is decided only by `ports:`, which is `127.0.0.1`.
- The config is mounted read-only (`:ro`), so a compromised SeaweedFS can't rewrite its own rules.
- Data lives in the named volume `seaweeddata` and survives `docker compose down` (not `down -v`).

### 3. Create the bucket (once)

```sh
echo "s3.bucket.create -name musicbox" | docker compose exec -T seaweedfs weed shell
```

`weed shell` is the admin console. It talks to the master on its internal port, which is only
reachable inside the container network. The API's S3 identity deliberately can't create
buckets, so this is the admin path.

## Using it from Go: `internal/storage`

```go
store, err := storage.New(storage.Config{
    Endpoint: os.Getenv("S3_ENDPOINT"), Bucket: os.Getenv("S3_BUCKET"),
    AccessKey: os.Getenv("S3_ACCESS_KEY"), SecretKey: os.Getenv("S3_SECRET_KEY"),
})
key, err := storage.AudioKey(sha256Hex)          // "audio/<sha256>", rejects anything else
err = store.Put(ctx, key, file, size, "audio/mpeg")
ok, err := store.Exists(ctx, key)                // HEAD: no download
body, err := store.Get(ctx, key)                 // caller must Close; ErrNotFound if missing
err = store.Delete(ctx, key)                     // missing key is not an error
err = store.Ping(ctx)                            // HEAD bucket: reachable, keys right, bucket exists
```

- Built with `s3.New(s3.Options{…})`, not the SDK's `config` package, which would also read
  `~/.aws`, `AWS_*` variables and the EC2 metadata service. See [security.md](security.md#go-modules).
- `UsePathStyle: true` gives `http://host/musicbox/key`. Virtual-host style
  (`http://musicbox.host/key`) needs a DNS name per bucket. With an IP endpoint like
  `127.0.0.1` the SDK falls back to path style anyway, but a hostname (the NAS) would break
  without it.
- `Region` is `us-east-1`. SeaweedFS ignores regions, but SigV4 signs the region name, so
  both sides must agree on one.
- Used by `POST /api/v1/tracks`. `cmd/api` builds it from the `S3_*` variables and calls `Ping` at startup, so wrong keys or a missing bucket stop the API immediately.

## Using it from the command line

The official AWS CLI, run in a container pinned by digest, so nothing is installed on the host:

```sh
set -a; . ./.env; set +a
export AWS_ACCESS_KEY_ID="$S3_ACCESS_KEY" AWS_SECRET_ACCESS_KEY="$S3_SECRET_KEY"
AWSCLI_IMAGE="amazon/aws-cli:2.37.13@sha256:d32864c20087d486f5988c3e70817d67a73f584a47535cada9ad97e0ea1e5196"

awscli() {
  docker run --rm --network host \
    --user "$(id -u):$(id -g)" -e HOME=/tmp \
    -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_DEFAULT_REGION=us-east-1 \
    -v /tmp:/tmp \
    "$AWSCLI_IMAGE" --endpoint-url "$S3_ENDPOINT" "$@"
}
```

- `-e AWS_ACCESS_KEY_ID` with no value copies it from the shell, so keys never appear on a
  command line (where `ps` and shell history would see them).
- `--user` runs as you, so files written to `/tmp` are yours.
- `--endpoint-url` is the only thing that differs from using real AWS.
- AWS CLI 2.37.13 was built 2026-10-12, the newest image at least two weeks old on 2026-10-27.

```sh
awscli s3 ls s3://musicbox/ --recursive              # list everything
awscli s3 cp ./song.mp3 s3://musicbox/audio/<sha256> # upload
awscli s3 cp s3://musicbox/audio/<sha256> ./out.mp3  # download
awscli s3 rm s3://musicbox/audio/<sha256>            # delete

echo "s3.bucket.list" | docker compose exec -T seaweedfs weed shell   # admin: list buckets
docker compose logs seaweedfs 2>&1 | grep -v LockRing | tail -50      # logs without the 30 s heartbeat
```

## Troubleshooting

**`SignatureDoesNotMatch` from `curl --aws-sigv4`, even with the right keys:** Ubuntu 22.04's
`curl` 7.81 signs the hash of an empty body and ignores the `x-amz-content-sha256` header you
pass, while SeaweedFS signs with the header's value. The two sides sign different text, so the
signatures differ on every request. `curl` 7.86+ honors the header. Use the AWS CLI above
instead of hand-signing.

**General rule:** signature errors almost always mean the client and server disagree about
*what* was signed (payload hash, headers, query string, region), not that the key is wrong. A
wrong *access key* gives `InvalidAccessKeyId` instead.

**`LockRing … received ring update` every 30 seconds** in the logs is a normal heartbeat
between the S3 gateway and the filer.
